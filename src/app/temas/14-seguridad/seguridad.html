14 — Seguridad / transversales

Conceptos que cruzan frontend y backend. En Angular suelen aparecer al autenticar una Persona (login, guards, interceptors).

JWT

JSON Web Token: credencial firmada (header.payload.signature). El front suele mandarla en Authorization: Bearer … vía interceptor HTTP. El guard puede leer claims (ej. rol de la Persona) para rutas admin.

  • Access token: corto (minutos)
  • Refresh token: más largo, idealmente en cookie HttpOnly

CORS

Política del navegador: un origen (ej. localhost:4200) no puede leer respuestas de otro (api.midominio.com) salvo que el servidor lo permita con headers (Access-Control-Allow-Origin, etc.).

No es un firewall de seguridad del API: es una restricción del browser. Postman / curl no aplican CORS.

XSS (Cross-Site Scripting)

Inyectar JS malicioso en tu página (ej. comentario con script). Si el token está en localStorage, el script lo puede leer y robar la sesión de la Persona.

  • Angular escapa por defecto en la interpolación del template
  • Cuidado con [innerHTML] / bypassSecurityTrust…
  • Nunca confíes solo en el front: sanitizá también en backend

CSRF (Cross-Site Request Forgery)

El browser manda cookies de sesión a tu API automáticamente en requests desde otro sitio. Un atacante puede “forzar” una acción autenticada.

  • Más crítico con cookies de sesión
  • Mitigaciones: token CSRF, SameSite cookies, no usar cookies para todo
  • JWT en header Authorization no se manda cross-site solo

Cookies vs JWT — ¿dónde guardar el token?

Lugar Pros Contras
Memoria (servicio Angular) No accesible fácil por XSS persistente Se pierde al refrescar
sessionStorage Muere al cerrar pestaña Vulnerable a XSS
localStorage Simple / persiste Vulnerable a XSS (evitar para access token)
Cookie HttpOnly + Secure JS no la lee (mejor ante XSS) Hay que cuidar CSRF / SameSite

Respuesta típica de entrevista: access token en memoria + refresh en cookie HttpOnly, o arquitectura BFF.
